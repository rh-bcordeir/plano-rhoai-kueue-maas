# Serving de LLMs no OpenShift AI 3.5, com Kueue (réplicas fixas)

**Plataforma:** Red Hat OpenShift AI 3.5 · OpenShift 4.22 · Distributed Inference with llm-d · Models-as-a-Service (MaaS) · Red Hat build of Kueue
**Modelos:** Qwen3.8-Flash-Next (FP8) e Qwen3.5-35B-A3B-FP8
**Hardware:** 1 nó com 4× NVIDIA H200 NVL e 2 nós com 10× NVIDIA RTX 4500 Ada cada

**Como usar este documento:**
- **Parte 1 – Arquitetura:** o que vai ser construído e por quê. Só conceitos e decisões, sem comandos.
- **Parte 2 – Implantação passo a passo:** tudo na ordem de execução, do cluster vazio até os modelos respondendo pelo MaaS. Cada etapa só usa o que as anteriores já instalaram.

# Parte 1: Arquitetura

## 1. Resumo das decisões

| Decisão | Escolha |
|---|---|
| Qwen3.8-Flash-Next | Só no nó H200, em **TEP2** (2 GPUs por réplica) |
| Qwen3.5-35B-A3B-FP8 | Só nos nós RTX: **TP4** em produção, **TP2** em homologação (EP opcional, decidido no teste de carga) |
| Réplicas | **Fixas**, definidas por teste de carga e alteradas só via GitOps (autoscaling WVA/KEDA é Technology Preview no 3.5) |
| Ambientes | Um namespace por **modelo × ambiente** (`prod-*` e `hml-*`) |
| Cotas e tipo de GPU | **Kueue**: um ClusterQueue por **tipo de GPU** (`cq-h200`, `cq-rtx`), cada um com um único ResourceFlavor, sem cohort; produção e homologação dividem a mesma fila |
| Prioridade entre workloads | `WorkloadPriorityClass` do Kueue: a produção preempta a homologação na mesma fila |
| Prioridade da aplicação crítica | **Flow control do llm-d** (GA), por requisição |
| Limite de tokens por consumidor | **MaaS**: subscriptions por grupo, authorization policies e API keys |
| Picos de demanda | Flow control (fila por prioridade, 429 para baixa prioridade) + limites do MaaS |

**O que o Kueue faz neste desenho:** com réplicas fixas, os servidores de inferência ocupam as GPUs o tempo todo, então para os modelos o Kueue funciona principalmente como **cota por tipo de GPU** e como **prioridade da produção sobre a homologação**: quando a produção precisa de GPU (mais réplicas ou rolling update), o Kueue tira a homologação, que volta sozinha quando a GPU fica livre. O valor maior dele aparece quando o cluster passar a rodar jobs que começam e terminam (fine-tuning, avaliação, batch), com fila, gang scheduling e preempção. Instalar desde já deixa a plataforma pronta para isso.

## 3. Dimensionamento dos modelos

### 3.1 Características

| | Qwen3.8-Flash-Next FP8 | Qwen3.5-35B-A3B-FP8 |
|---|---|---|
| Arquitetura | MoE: 125B + 51B de tabela N-gram + 4B MTP; ~6B ativos | MoE: 35B, ~3B ativos |
| Experts | 512, dimensão interna 640 | 256, dimensão interna 512 |
| Checkpoint | 172,78 GiB | ~35 GiB (estimativa; confirmar) |
| Tabela N-gram | ≈ 47,7 GiB em FP8; pode ir para a RAM do host | não tem |
| Paralelismo | **TP2 ou TP4 funcionam**; **TP8 é incompatível** com o FP8 (640 ÷ 8 = 80, menor que um bloco de 128). **TEP recomendado** por desempenho | **TP puro funciona** (512 ÷ 4 = 128); EP opcional |
| vLLM | ≥ 0.30.0 | versões recentes |

### 3.2 GPUs

| | H200 NVL | RTX 4500 Ada |
|---|---|---|
| Memória | 141 GB HBM3e | 24 GB GDDR6 |
| Banda | ~4,8 TB/s | 432 GB/s |
| Interconexão | NVLink bridge | PCIe 4.0, sem NVLink |

### 3.3 Por que cada modelo fica onde fica

```
VRAM necessária ≈ pesos + KV cache / estado recorrente + ativações + overhead
VRAM utilizável = VRAM × --gpu-memory-utilization (0,85–0,90)
```

| | Flash-Next em 8× RTX (TEP8) | Flash-Next em 2× H200 (TEP2) |
|---|---|---|
| VRAM utilizável por GPU | ~21,6 GiB | ~126 GiB |
| Pesos por GPU (N-gram na RAM) | ~16,5 GiB | ~63,5 GiB |
| Sobra para cache | **~3 GiB** | **~59 GiB** |

- **Flash-Next nas RTX** só cabe com 8 GPUs (1, 2, 4 ou 8 são válidos), offload obrigatório do N-gram, pouca concorrência e comunicação pesada via PCIe. As mesmas 8 RTX servem 2 réplicas TP4 de produção do Qwen3.5.
- **Qwen3.5 nas RTX:** TP4 deixa ~40 GiB de cache por réplica; TP2 deixa ~8–10 GiB, suficiente para testes funcionais.

```
┌──────────── Nó H200 · 4× H200 NVL ──────────────────────────────┐
│ [GPU0][GPU1]   Flash-Next PROD · TEP2 · 1 réplica               │
│ [GPU2][GPU3]   Flash-Next HML  · TEP2 · 1 réplica               │
└─────────────────────────────────────────────────────────────────┘
┌──────────── Nó RTX 1 · 10× RTX 4500 Ada ────────────────────────┐
│ [0][1][2][3]   Qwen3.5 PROD · TP4 · réplica A                   │
│ [4][5][6][7]   Qwen3.5 PROD · TP4 · réplica B                   │
│ [8][9]         Qwen3.5 HML  · TP2 · réplica 1                   │
└─────────────────────────────────────────────────────────────────┘
┌──────────── Nó RTX 2 · 10× RTX 4500 Ada ────────────────────────┐
│ [0][1][2][3]   Qwen3.5 PROD · TP4 · réplica C                   │
│ [4][5][6][7]   Qwen3.5 PROD · TP4 · réplica D                   │
│ [8][9]         Qwen3.5 HML  · TP2 · réplica 2                   │
└─────────────────────────────────────────────────────────────────┘
```

| Modelo / ambiente | Namespace | Réplicas × GPUs | Total | ClusterQueue |
|---|---|---|---|---|
| Flash-Next produção | `prod-flashnext` | 1 × 2 H200 | 2 | `cq-h200` |
| Flash-Next homologação | `hml-flashnext` | 1 × 2 H200 | 2 | `cq-h200` |
| Qwen3.5 produção | `prod-qwen35` | 4 × 4 RTX (2 por nó) | 16 | `cq-rtx` |
| Qwen3.5 homologação | `hml-qwen35` | 2 × 2 RTX (1 por nó) | 4 | `cq-rtx` |
| **Total** | | | **24 de 24** | |

**Variantes, decididas no teste de carga:**
- **Flash-Next com 2 × TEP2 na produção:** basta mudar a produção para `replicas: 2`. O Kueue tira a homologação do Flash-Next, e ela volta sozinha quando a produção retornar a 1 réplica. Não precisa mexer na cota.
- **Flash-Next com 1 × TEP4 na produção:** mudar o número de GPUs **por pod** (de 2 para 4, ou de volta) com a fila cheia **trava**: o pod antigo segura as GPUs com a mesma prioridade, e tirar a homologação não libera o suficiente, então o Kueue não preempta ninguém. A troca exige **janela de manutenção** com a produção fora do ar (Etapa 9.4).
- **Qwen3.5:** se 3 réplicas TP4 bastarem para a produção, a homologação pode ganhar 1 réplica TP4 (igual à produção) + 2 TP2.
- **Não misture TP4 e TP2 na produção:** cada `LLMInferenceService` tem um único tamanho de réplica e seu próprio pool; misturar exigiria dois serviços com divisão de tráfego por peso fixo.

**Pontos de atenção:**
- **Nó H200 único:** o Flash-Next não tem HA entre nós.
- **O Kueue não escolhe o nó.** Ele admite pela cota do flavor (20 GPUs RTX somando os dois nós); quem posiciona os pods é o scheduler. Sem regra de espalhamento, as duas réplicas de homologação podem cair no mesmo nó e deixar a 4ª réplica de produção sem lugar (4 GPUs livres, mas 2 + 2). Por isso o Qwen3.5 usa `topologySpreadConstraints` por nó.

## 5. Kueue no desenho

### 5.1 Objetos

| Objeto | O que define | Neste desenho |
|---|---|---|
| **ResourceFlavor** | Um tipo de nó (labels + tolerations) | `h200-nvl` e `rtx4500-ada` |
| **ClusterQueue** | Cota por flavor e regras de preempção | 2 filas, uma por tipo de GPU: `cq-h200` e `cq-rtx` |
| **LocalQueue** | Porta de entrada da fila dentro de um namespace | uma por namespace de modelo, apontando para a fila do tipo de GPU |
| **WorkloadPriorityClass** | Prioridade de admissão e preempção dentro da fila | `prod-critico`, `prod`, `hml` |
| **Hardware profile** | Perfil do dashboard ligado a uma LocalQueue | um por projeto |

### 5.2 Cotas

| ClusterQueue | Flavor | GPUs | Namespaces | Uso no layout base |
|---|---|---|---|---|
| `cq-h200` | `h200-nvl` | 4 | `prod-flashnext`, `hml-flashnext` | produção 2 + homologação 2 |
| `cq-rtx` | `rtx4500-ada` | 20 | `prod-qwen35`, `hml-qwen35` | produção 16 + homologação 4 |

**Cota = capacidade física** de cada tipo de GPU. A cota só muda quando entram ou saem GPUs do cluster, não quando muda o layout.

**Como produção e homologação convivem na mesma fila:**

| Situação | O que acontece |
|---|---|
| Produção sobe réplicas com a fila cheia | O Kueue tira pods da homologação (`withinClusterQueue: LowerPriority`). O pod removido fica `SchedulingGated` |
| Produção volta ao número original de réplicas | A homologação é admitida de novo, sem intervenção |
| Rolling update da produção com a fila cheia | O pod novo preempta a homologação, o antigo sai e a homologação volta |
| Rolling update da homologação com a fila cheia | **Trava**: a homologação não preempta a produção. Usar `replicas: 0 → N` |
| Produção muda o número de GPUs **por pod** com a fila cheia | **Trava** (ver 4, variante TEP4). Usar `replicas: 0 → N` em janela de manutenção |

A homologação fica fora do ar sempre que a produção escala ou atualiza, durante o tempo de recarregar o modelo. Com o Flash-Next, sem modelcar ou PVC, isso pode levar muito tempo.

### 5.3 Restrições do OpenShift AI 3.5 que moldam o desenho

- **Sem shared cohorts:** cada ClusterQueue é independente. Não há empréstimo de cota nem preempção entre filas. Por isso produção e homologação ficam **na mesma fila**: é a única forma de a prioridade valer entre elas.
- **Um flavor por ClusterQueue:** `cq-h200` lista só `h200-nvl` e `cq-rtx` lista só `rtx4500-ada`. Não acrescente outro flavor à mesma fila: o Kueue tenta os flavors na ordem e, com o RTX cheio, admitiria um Qwen3.5 na H200.
- **Hardware profiles sem node selectors/tolerations** em namespaces gerenciados pelo Kueue: o tipo de GPU vem do ResourceFlavor.
- **Kueue em modo `Unmanaged`** no DataScienceCluster (o modo `Managed`, embutido, está depreciado e conflita com o Red Hat build of Kueue).
- **Namespaces gerenciados** precisam do label `kueue.openshift.io/managed=true`.
- **A prioridade é por fila:** a `WorkloadPriorityClass` só atua dentro de um mesmo ClusterQueue. Com uma fila por tipo de GPU, `prod-critico` (1000) e `hml` (100) disputam a mesma cota, e a produção vence.
- **`spec.clusterQueue` da LocalQueue é imutável:** para mudar a fila de um namespace, apague e recrie a LocalQueue.

### 5.4 Taints nos nós de GPU

Os nós de GPU recebem um taint com a chave **`nvidia.com/gpu`** e o tipo no valor (`h200nvl`, `rtx4500ada`), para manter workloads sem GPU fora deles. Essa chave já é tolerada pelos DaemonSets do GPU Operator. A toleration dos modelos é injetada pelo **ResourceFlavor**, junto com o node selector.

## 6. Acesso, limites e prioridade

**MaaS (quem acessa e quanto):**

| Subscription | Grupo | Modelos | Limite (exemplo, calibrar) |
|---|---|---|---|
| `app-critica` | `grp-app-critica` | produção | alto, ex.: 2M tokens/min |
| `prod-consumidores` | `grp-prod-apps` | produção | médio, ex.: 300k tokens/min |
| `hml-devs` | `grp-desenvolvedores` | só `*-hml` | baixo, ex.: 100k tokens/min |

Regra de dimensionamento: **soma dos limites de produção ≤ capacidade medida das réplicas de produção.**

**Flow control:** o Kueue prioriza **pods**; o flow control prioriza **requisições** dentro do mesmo modelo. A aplicação crítica recebe prioridade 100 e os demais consumidores 0. Fora de saturação não há fila nem latência extra.

## 7. Riscos e itens a validar

| # | Item | Impacto | Mitigação |
|---|---|---|---|
| 1 | **Kueue gerenciando `LLMInferenceService`** | Sem cota, tipo de GPU e prioridade via Kueue | **Validado (RHOAI 3.5.2 + Kueue 1.5.0):** os labels `kueue.x-k8s.io/*` do `LLMInferenceService` passam para o Deployment, o Kueue cria o Workload, admite pela cota e o flavor injeta nodeSelector e toleration. Revalidar a cada upgrade (Etapa 10.1) |
| 2 | Como o Kueue contabiliza o `LLMInferenceService` e quais `frameworks` habilitar | Admissão diferente do esperado | **Validado:** um Workload **por pod** (`pod-<nome-do-pod>-*`); `BatchJob`, `Deployment` e `Pod` no Kueue CR são suficientes. O pod do scheduler (EPP) não usa GPU e não gera Workload |
| 3 | Imagem vLLM do RHOAI 3.5 suporta o Qwen3.8-Flash-Next (arquitetura `Qwen4ExpForConditionalGeneration`; a receita pede vLLM ≥ 0.30.0) | Modelo não sobe com imagem suportada | O RHOAI 3.5.2 traz o vLLM **0.24.0** (`vllm-0.24.0+rhaiv.15`). Confirmar se a arquitetura está registrada na imagem (Etapa 10, "Antes de começar"); se não estiver, usar imagem vLLM própria no container `main` (fora do suporte da Red Hat para o vLLM) |
| 4 | TEP2 do Flash-Next em H200 (fora das configs da receita) | Erro de inicialização ou memória | Testar TP4/TEP4 com as 4 H200 |
| 5 | Toleration dos DaemonSets do GPU Operator | Driver/device plugin parados após o taint | Conferir antes e depois do taint (Etapa 9) |
| 6 | Fragmentação nos nós RTX | 4ª réplica `Pending` com cota livre | `topologySpreadConstraints` + produção antes da homologação |
| 7 | Rolling update com a fila cheia (**reproduzido**: o pod novo fica `SchedulingGated` enquanto o antigo, mesmo em CrashLoop, segura a cota) | Atualização travada | Produção: **não trava**, o pod novo preempta a homologação (testado). Homologação e mudança de GPUs por pod: travam. `maxSurge: 0` e `Recreate` **não são configuráveis** (o `LLMInferenceService` não expõe a estratégia e o controller reverte patches no Deployment). Usar `replicas: 0 → N` |
| 8 | Flow control com API key do MaaS: o `maas-default-gateway` **não injeta** `x-gateway-inference-objective` (só o gateway `openshift-ai-inference` injeta) e **não bloqueia** esse cabeçalho vindo do cliente | App crítica sem prioridade; qualquer consumidor pode se declarar crítico | Definir como o cabeçalho será fixado no gateway do MaaS (ex.: AuthPolicy própria que sobrescreve o valor a partir do grupo/subscription) antes de usar o flow control em produção |
| 9 | RAM do nó H200 (offload do N-gram) | OOM no host | ~96 Gi por pod de Flash-Next |
| 10 | Nó H200 único | Flash-Next indisponível em falha/manutenção | Janela planejada e fallback |
| 11 | P2P entre RTX via PCIe | Latência maior no TP4 | `nvidia-smi topo -m`; comparar TP4 x TEP4 |
| 12 | Homologação preemptada sempre que a produção escala ou atualiza | Homologação fora do ar até recarregar o modelo | Pesos em modelcar ou PVC; avisar os times de homologação antes de mudanças em produção |
| 13 | Preempção nos nós RTX (não testado): o Kueue admite pela cota somada dos dois nós, e a GPU liberada por uma homologação TP2 pode estar no nó errado para uma réplica TP4 | Pod de produção admitido, mas `Pending` | Validar com os nós reais; `topologySpreadConstraints` na produção e na homologação |
| 14 | Timeout de 200 ms da autenticação do Authorino no plugin WASM do RHCL (RHOAIENG-71638, known issue do 3.4/3.5; não reproduzido no lab) | HTTP 500/503 no MaaS sob carga concorrente, com modelos saudáveis; distorce o teste de carga | `AUTH_SERVICE_TIMEOUT=2s` na Subscription do RHCL (Etapa 6.5) antes da Etapa 11 |

### Etapa 5: Red Hat build of Kueue

**5.1 Instalar o operador**

1. No web console, procure **Red Hat build of Kueue** e clique em **Install**.
2. Mantenha o namespace sugerido (`openshift-kueue-operator`), o canal estável mais recente e a aprovação automática.

**5.2 Criar o Kueue CR**

O nome precisa ser `cluster`. Criá-lo explicitamente permite escolher as integrações:

```yaml
apiVersion: kueue.openshift.io/v1
kind: Kueue
metadata:
  name: cluster
  namespace: openshift-kueue-operator
spec:
  managementState: Managed
  config:
    integrations:
      frameworks:
      - BatchJob
      - Deployment      # workloads de serving
      - Pod
    preemption:
      preemptionPolicy: Classical
```

```bash
oc apply -f kueue-cr.yaml
oc get kueues.kueue.openshift.io -A    # nome completo: depois do RHOAI, "kueue" resolve para o CRD do RHOAI
oc get pods -n openshift-kueue-operator
# kueue-controller-manager-*   1/1 Running   (2 réplicas)
# openshift-kueue-operator-*   1/1 Running   (2 réplicas)
```

> A documentação do 3.5 não diz quais `frameworks` o Kueue precisa para enxergar os pods do `LLMInferenceService`. A lista acima foi validada com RHOAI 3.5.2 e Kueue 1.5.0; a Etapa 10.1 confirma no seu cluster.

**6.5 Timeout de autenticação do Authorino (RHOAIENG-71638)**

Known issue do RHOAI 3.4 e 3.5, descrita na release note. Não foi reproduzida neste laboratório. O RHCL configura o plugin WASM do Kuadrant com timeout de autenticação de **200 ms** e `failureMode: deny`. Sob muitas requisições concorrentes, quando o cache do Authorino falha, a autenticação passa desse tempo e o MaaS devolve **HTTP 500 ou 503**, mesmo com os modelos saudáveis. Isso afeta o teste de carga da Etapa 11: os erros parecem falta de capacidade, mas vêm da autenticação.

Workaround da release note: `AUTH_SERVICE_TIMEOUT=2s` na Subscription do operador do RHCL. Com a instalação da 6.1, a Subscription é `rhcl-operator` em `openshift-operators`. Confira o nome e se ela já tem `spec.config`:

```bash
oc get subscription -n openshift-operators | grep rhcl
oc get subscription rhcl-operator -n openshift-operators -o jsonpath='{.spec.config}{"\n"}'
```

Sem `spec.config` (saída vazia), que é o caso de uma instalação nova:

```bash
oc patch subscription rhcl-operator -n openshift-operators --type json \
  -p '[{"op":"add","path":"/spec/config","value":{"env":[{"name":"AUTH_SERVICE_TIMEOUT","value":"2s"}]}}]'
```

Se `spec.config` já existir, use `"path":"/spec/config/env"` com o valor `[{"name":"AUTH_SERVICE_TIMEOUT","value":"2s"}]`. Se `spec.config.env` já existir, use `"path":"/spec/config/env/-"` com o valor `{"name":"AUTH_SERVICE_TIMEOUT","value":"2s"}`.

Aguarde o operador reiniciar:

```bash
oc wait --for=jsonpath='{.status.state}'=AtLatestKnown subscription/rhcl-operator -n openshift-operators --timeout=300s
oc wait --for=condition=Available deployment/kuadrant-operator-controller-manager -n openshift-operators --timeout=120s
```

Confira no gateway do MaaS (a mudança chega em cerca de 1 minuto; antes do patch aparece `200ms`):

```bash
oc get envoyfilter kuadrant-maas-default-gateway -n openshift-ingress -o json \
  | grep -o 'auth-service[^}]*' | grep -o 'timeout[^,]*'      # timeout ... 2s
```

> Procedimento aplicado e verificado no laboratório: o `auth-service` passou de `200ms` para `2s`, o `failureMode` continuou `deny` e os modelos seguiram respondendo pelo MaaS.

**8.1 Gateway de inferência do llm-d**

O llm-d usa o `Gateway` `openshift-ai-inference` em `openshift-ingress`. O Service Mesh 3 já vem no OpenShift 4.20+. **O Service Mesh v2 não pode estar instalado.**


No 3.5.2 o RHOAI **não** cria o gateway `openshift-ai-inference` nem uma GatewayClass com esse nome. Crie o certificado e o gateway, restrito por label de namespace (nunca `from: All`):


```yaml
apiVersion: gateway.networking.k8s.io/v1

  name: openshift-ai-inference
  namespace: openshift-ingress
  labels:
    istio.io/rev: openshift-gateway

  - name: https
    port: 443
    protocol: HTTPS
```

> **Opcional: usar só o gateway do MaaS** (testado no RHOAI 3.5.2). Se todo acesso aos modelos for pelo MaaS, o `openshift-ai-inference` pode ser dispensado:
> 1. Todo `LLMInferenceService` precisa de `router.gateway.refs` apontando para o `maas-default-gateway` (já é o caso nos YAMLs das Etapas 10 e 12). O KServe continua usando `openshift-ai-inference` como padrão: sem `refs`, o serviço fica `Ready=False` com `RefsInvalid ... non-existent Gateway openshift-ingress/openshift-ai-inference`.
> 2. Não crie o gateway desta etapa, ou apague-o com `oc delete gateway openshift-ai-inference -n openshift-ingress`. Saem juntos o Deployment, o load balancer, a AuthPolicy `openshift-ai-inference-authn` e o EnvoyFilter; o RHOAI não recria o gateway.
> 3. O label `inference-gateway-access` deixa de ser necessário nos namespaces (Etapa 9.2); basta `maas-gateway-access`.
> 4. Para não repetir o bloco `router` em cada serviço, dá para usar um `LLMInferenceServiceConfig` com `labels: { opendatahub.io/config-type: router }` e o `router.gateway.refs` do MaaS, referenciado no serviço por `spec.baseRefs` (testado com o template no mesmo namespace do serviço).
>
> Perde-se o acesso aos modelos sem MaaS (token do OpenShift) e a injeção de `x-gateway-inference-objective` feita pela AuthPolicy desse gateway (Etapa 14).

**9.4 ClusterQueues (um por tipo de GPU, sem cohort)**

Produção e homologação do mesmo modelo entram na mesma fila. A preempção por prioridade (`withinClusterQueue: LowerPriority`) é o que dá a GPU à produção.

```yaml
apiVersion: kueue.x-k8s.io/v1beta2
kind: ClusterQueue
metadata:
  name: cq-h200
spec:
  namespaceSelector:
    matchExpressions:
    - { key: kubernetes.io/metadata.name, operator: In, values: [prod-flashnext, hml-flashnext] }
  preemption:
    withinClusterQueue: LowerPriority
  resourceGroups:
  - coveredResources: ["nvidia.com/gpu", "cpu", "memory"]
    flavors:
    - name: h200-nvl
      resources:
      - { name: nvidia.com/gpu, nominalQuota: 4 }     # todas as H200
      - { name: cpu,            nominalQuota: 64 }
      - { name: memory,         nominalQuota: 256Gi }
---
apiVersion: kueue.x-k8s.io/v1beta2
kind: ClusterQueue
metadata:
  name: cq-rtx
spec:
  namespaceSelector:
    matchExpressions:
    - { key: kubernetes.io/metadata.name, operator: In, values: [prod-qwen35, hml-qwen35] }
  preemption:
    withinClusterQueue: LowerPriority
  resourceGroups:
  - coveredResources: ["nvidia.com/gpu", "cpu", "memory"]
    flavors:
    - name: rtx4500-ada
      resources:
      - { name: nvidia.com/gpu, nominalQuota: 20 }    # todas as RTX (10 + 10)
      - { name: cpu,            nominalQuota: 160 }
      - { name: memory,         nominalQuota: 640Gi }
```

CPU e memória são exemplos; ajuste ao hardware.

**Rolling updates.** O Deployment gerado usa `maxSurge: 25%` (com poucas réplicas, arredonda para 1 pod extra): o pod novo sobe antes de o antigo sair. O `LLMInferenceService` **não expõe** a estratégia de rollout (nem `maxSurge`, nem `Recreate`), e o controller reverte patches no Deployment. Com a fila cheia:

- **Produção:** o pod novo preempta a homologação e a atualização anda. A homologação volta quando a produção terminar.
- **Homologação:** o pod novo fica `SchedulingGated`, porque não preempta a produção. Passe por `replicas: 0` e volte ao valor original.

**Mudar o número de GPUs por pod** (ex.: Flash-Next de TEP2 para TEP4, ou de volta). Altere juntos o `--tensor-parallel-size` e o `nvidia.com/gpu` em `requests` e `limits`: o Kueue só enxerga o `resources`, e o vLLM só enxerga o argumento. Com a fila cheia, o pod novo trava ("4 more needed" / "2 more needed"): o antigo segura as GPUs com a mesma prioridade, e tirar a homologação não libera o suficiente, então o Kueue não preempta ninguém. Aumentar a `nominalQuota` não resolve, porque as GPUs físicas continuam ocupadas. Faça em **janela de manutenção**:

```bash
oc patch llminferenceservice flashnext-prod -n prod-flashnext --type merge -p '{"spec":{"replicas":0}}'
# altere --tensor-parallel-size e nvidia.com/gpu (requests e limits) no YAML e aplique (GitOps)
oc patch llminferenceservice flashnext-prod -n prod-flashnext --type merge -p '{"spec":{"replicas":1}}'
oc get workloads -n hml-flashnext       # com TEP4, a homologação fica pendente (sem cota)
```

A produção fica fora do ar até o pod novo carregar o modelo.

**Teto opcional para a homologação.** Na mesma fila, a homologação pode usar as GPUs que a produção não está usando (e perde quando a produção precisar). Para limitar o quanto ela pega, use um `ResourceQuota` no namespace (testado: uma réplica acima do teto é recusada na criação, mesmo com cota livre no Kueue):

```yaml
apiVersion: v1
kind: ResourceQuota
metadata: { name: gpu-cap, namespace: hml-qwen35 }
spec:
  hard:
    requests.nvidia.com/gpu: "4"
```

Com o teto igual ao uso, o rolling update da homologação é recusado já no `ResourceQuota`. O `replicas: 0 → N` continua sendo a saída.

### Etapa 14: flow control (prioridade da aplicação crítica)

No gateway `openshift-ai-inference`, a AuthPolicy `openshift-ai-inference-authn` define o cabeçalho `x-gateway-inference-objective` pela autenticação: com token de ServiceAccount, o valor é o **namespace** da ServiceAccount; com token de usuário, `authenticated`.

> **Atenção, MaaS:** os modelos deste desenho ficam no `maas-default-gateway`, e a AuthPolicy dele (`maas-gateway-auth`) **não define** `x-gateway-inference-objective`; ela injeta só `X-MaaS-Group` e `X-MaaS-Subscription`. Ela também **não bloqueia** esse cabeçalho vindo do cliente, então qualquer consumidor poderia enviar `x-gateway-inference-objective: app-critica`. Antes de depender do flow control em produção, defina como o valor será fixado no gateway a partir da identidade (ex.: uma AuthPolicy/política de cabeçalhos que sobrescreva o valor conforme a subscription) e valide sob carga.

```yaml
apiVersion: llm-d.ai/v1alpha2
kind: InferenceObjective
metadata:
  name: app-critica                 # = valor do cabeçalho para a aplicação crítica
  namespace: prod-qwen35
spec:
  priority: 100
  poolRef:
    group: inference.networking.k8s.io
    name: qwen35-prod-inference-pool
---
apiVersion: llm-d.ai/v1alpha2
kind: InferenceObjective
metadata:
  name: authenticated
  namespace: prod-qwen35
spec:
  priority: 0
  poolRef:
    group: inference.networking.k8s.io
    name: qwen35-prod-inference-pool
```

> **`poolRef.group`:** o InferencePool criado pelo `LLMInferenceService` é do grupo `inference.networking.k8s.io` e se chama `<nome-do-llminferenceservice>-inference-pool` (`oc get inferencepools.inference.networking.k8s.io -n prod-qwen35`). Com `group: llm-d.ai`, o objective é aceito pela API, mas o EPP o **ignora sem nenhum erro**. Para conferir: `oc logs -n prod-qwen35 deploy/qwen35-prod-kserve-router-scheduler | grep 'Added/Updated InferenceObjective'`.

Repita em `prod-flashnext`. Configure o detector de saturação na configuração do scheduler (EndpointPicker), com `maxTokenConcurrency` calibrado na Etapa 11:

```yaml
plugins:
- name: concurrency-detector
  type: concurrency-detector
  parameters:
    concurrencyMode: "tokens"
    maxTokenConcurrency: <calibrar>
    headroom: 0.2
- name: inflight-load-producer
  type: inflight-load-producer
  parameters:
    addEstimatedOutputTokens: true
flowControl:
  saturationDetector:
    pluginRef: concurrency-detector
```

Valide com carga mista: sob saturação, `llm_d_epp_flow_control_queue_size` deve crescer nas bandas de menor prioridade, não na da aplicação crítica. Os clientes devem tratar HTTP 429/503 com retry e backoff.

### Erros comuns

| Sintoma | Causa provável | Correção |
|---|---|---|
| Autenticação do llm-d não funciona | Pré-requisitos fora de ordem | Recriar Gateway, Kuadrant e Authorino na ordem e reiniciar `odh-model-controller` e `kserve-controller-manager` |
| Modelos inacessíveis após instalar o Connectivity Link | OpenShift AI instalado antes do Kuadrant | `oc delete pod -n redhat-ods-applications -l app=odh-model-controller` e `-l control-plane=kserve-controller-manager` |
| Tenant do MaaS `Degraded` | UWM, secret do banco ou Kuadrant | Ver Etapa 8.5 |
| HTTP 429 sem consumo | Authorization policy sem subscription | Criar a subscription |
| HTTP 403 | Subscription sem authorization policy | Criar a policy |
| Gateway não roteia para o modelo | Namespace sem o label do `allowedRoutes` | Aplicar o label (Etapa 9.2) |
| "Queue does not exist" | LocalQueue ausente no namespace | Criar a LocalQueue (Etapa 9.5) |
| Pods sobem sem Workload do Kueue | Kueue não gerencia o recurso | Ver Etapa 10.1 |
| Workload pendente com GPU livre | Cota do ClusterQueue esgotada ou flavor errado | `oc describe clusterqueue` e `oc describe workload` |
| Kueue em conflito | Kueue embutido (`Managed`) junto com o Red Hat build of Kueue | Usar `managementState: Unmanaged` |
| Pods do GPU Operator param após o taint | Toleration customizada na `ClusterPolicy` | Ajustar `daemonsets.tolerations` |
| 4ª réplica de produção `Pending` | Fragmentação | Conferir o spread e a ordem de deploy |
| Rolling update da homologação travado (pod novo `SchedulingGated`) | Fila cheia; homologação não preempta produção | `replicas: 0 → N` (`maxSurge` e `Recreate` não são configuráveis) |
| Pod novo da produção travado com "4 more needed" ou "2 more needed" | Mudou o número de GPUs por pod com a fila cheia | `replicas: 0 → N` em janela de manutenção (9.4) |
| Homologação `SchedulingGated` sem ter mudado nada | Preemptada pela produção (escala ou rolling update) | Esperado; volta sozinha quando a produção libera GPU |
| Erro ao editar `spec.clusterQueue` da LocalQueue | Campo imutável | Apagar e recriar a LocalQueue (9.5) |
| Operador abre "ClusterExtensions" | Catálogo OLMv1 (OCP 4.21+) | Desabilitar o OLMv1 antes de instalar |
| Kuadrant `MissingDependency: Gateway API provider` | GatewayClass `openshift-default` ausente | Etapa 6.2 e reiniciar o operador do Kuadrant |
| Gateway `PROGRAMMED=Unknown` | GatewayClass inexistente ou secret TLS ausente | Usar `openshift-default` e criar o secret (8.1/8.3) |

# Apêndices

## A. TP, TEP e por que cada modelo usa um

**TEP = Tensor Parallelism + Expert Parallelism** (`--tensor-parallel-size N --enable-expert-parallel`): atenção e camadas densas fatiadas em N; experts distribuídos inteiros entre as N GPUs.

Com **TP puro**, cada expert é fatiado entre as GPUs. O checkpoint FP8 usa quantização em **blocos de 128**, e a fatia de cada GPU não pode ser menor que um bloco. Com **TEP**, os experts não são fatiados (cada GPU recebe experts inteiros), então essa restrição não se aplica.

| Modelo | Dimensão do expert | Fatia por GPU em TP2 / TP4 / TP8 | TP puro | Recomendação |
|---|---|---|---|---|
| Qwen3.8-Flash-Next | 640 | 320 / 160 / **80** | TP2 e TP4 funcionam; **TP8 incompatível** (80 < 128) | **TEP**, por desempenho (a receita do vLLM indica que expert parallelism é consistentemente mais rápido para este modelo) |
| Qwen3.5-35B-A3B | 512 | 256 / 128 / 64 | TP2 e TP4 funcionam | **TP**; EP opcional, decidido no teste de carga |

Sem NVLink (RTX), mantenha N pequeno (2 ou 4).

## B. Tabela N-gram

```
20.000.000 entradas × 2.560 = 51,2 × 10⁹ parâmetros
FP8 (1 byte)               = 51,2 GB ≈ 47,7 GiB
Por GPU (só via TP)        = 47,7 GiB ÷ nº de GPUs
Resto do checkpoint        = 172,78 − 47,7 ≈ 125 GiB
```

A tabela fica inteira na GPU (dividida por TP) ou inteira na RAM do host.
