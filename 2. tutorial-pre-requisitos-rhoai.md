# Tutorial: pré-requisitos e instalação base do OpenShift AI 3.5 para serving de LLMs

**Objetivo:** preparar o cluster para a arquitetura descrita em `arquitetura-llm-ocp.md` (llm-d + MaaS + Kueue), cobrindo tudo o que vem **antes** de criar filas do Kueue, fazer deploy de modelos e configurar subscriptions.

**Base:** documentação Red Hat OpenShift AI Self-Managed 3.5 e OpenShift Container Platform 4.22 (*AI workloads*).
**Pré-requisito geral:** OpenShift 4.19 ou superior, acesso `cluster-admin`, `oc` instalado e uma storage class padrão com provisionamento dinâmico.

> **A ordem importa.** A documentação de troubleshooting do llm-d avisa que autenticação quebrada e modelos inacessíveis costumam vir de pré-requisitos instalados fora de ordem. Siga as fases na sequência.

---

## Visão geral

| Fase | O que faz | Necessário para |
|---|---|---|
| 0 | Login e verificações iniciais | Tudo |
| 1 | GPUs: NFD + NVIDIA GPU Operator | Modelos |
| 2 | User Workload Monitoring | MaaS (sem ele fica `Degraded`), métricas do vLLM |
| 3 | cert-manager | KServe, llm-d, Kueue, MaaS |
| 4 | Red Hat build of Kueue | Cotas e prioridade |
| 5 | LeaderWorkerSet (opcional) | Só multi-nó (> 8 GPUs por servidor) |
| 6 | Red Hat Connectivity Link (Kuadrant + Authorino) | Autenticação do llm-d, MaaS |
| 7 | Operador do OpenShift AI e DataScienceCluster | Plataforma |
| 8 | Gateway de inferência do llm-d | Expor modelos |
| 9 | PostgreSQL, gateway e TLS do MaaS | MaaS |
| 10 | Habilitar MaaS no DataScienceCluster e no dashboard | MaaS |
| 11 | Verificação final | — |

> **OpenShift 4.21 ou superior:** o catálogo OLMv1 vem habilitado como Technology Preview. Ao instalar operadores pelo OperatorHub, você pode cair numa página de *ClusterExtensions* em vez do formulário padrão. A documentação recomenda desabilitar o catálogo OLMv1 antes de instalar (ver *Troubleshooting common installation problems*).

> **Instalação dos operadores:** todos os operadores deste tutorial são instalados pelo web console, em **Ecosystem → Software Catalog** (OpenShift 4.20+) ou **Operators → OperatorHub** (4.19). Depois de cada instalação, confira em **Installed Operators** se o status é **Succeeded**.

## Fase 1: GPUs (Node Feature Discovery + NVIDIA GPU Operator)

A documentação do OpenShift AI remete ao guia da NVIDIA (*NVIDIA GPU Operator on Red Hat OpenShift*). Pontos obrigatórios:

1. **Instale o Node Feature Discovery (NFD)** pelo web console (**Ecosystem → Software Catalog** (OpenShift 4.20+) ou **Operators → OperatorHub** (4.19)) e **crie uma instância de `NodeFeatureDiscovery`** com os valores padrão.
2. **Instale o NVIDIA GPU Operator** pelo mesmo caminho e **crie uma `ClusterPolicy`** com os valores padrão.
3. **Aguarde** os pods do GPU Operator ficarem prontos (driver, toolkit, device plugin, DCGM).

Verificação:

```bash
# GPUs anunciadas nos nós
oc describe node <no-h200> | grep -A3 -i 'nvidia.com/gpu'
oc describe node <no-rtx>  | grep -A3 -i 'nvidia.com/gpu'

# Labels usados depois nos ResourceFlavors do Kueue
oc get nodes -L nvidia.com/gpu.product -L nvidia.com/gpu.count

# Topologia entre GPUs (importante para TP nas RTX, que só têm PCIe)
oc exec -n nvidia-gpu-operator <pod-nvidia-driver-daemonset> -- nvidia-smi topo -m
```

Anote o valor exato de `nvidia.com/gpu.product` dos nós H200 e RTX: ele vai nos `ResourceFlavor` do Kueue.

> **Depois de instalar o OpenShift AI (Fase 7):** a documentação pede para apagar o ConfigMap `migration-gpu-status` em `redhat-ods-applications` e reiniciar o deployment `rhods-dashboard`. O passo está repetido na Fase 7.

## Fase 2: User Workload Monitoring

Necessário para o MaaS (sem ele o tenant do MaaS fica `Degraded`) e para coletar as métricas do vLLM e do flow control.

```bash
oc get configmap cluster-monitoring-config -n openshift-monitoring
```

Se não existir, crie. Se existir, **edite** e acrescente a chave (não sobrescreva outras configurações):

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    enableUserWorkload: true
```

```bash
oc apply -f cluster-monitoring-config.yaml
# ou: oc edit configmap cluster-monitoring-config -n openshift-monitoring
```

Verificação:

```bash
oc get pods -n openshift-user-workload-monitoring
# devem aparecer prometheus-operator, prometheus-user-workload-* e thanos-ruler-*
```

## Fase 4: Red Hat build of Kueue

### 4.1 Instalar o operador

1. No web console, abra **Ecosystem → Software Catalog** (OpenShift 4.20+) ou **Operators → OperatorHub** (4.19).
2. Procure **Red Hat build of Kueue** e clique em **Install**.
3. Mantenha o namespace sugerido (`openshift-kueue-operator`), o canal estável mais recente e a aprovação automática.
4. Clique em **Install** e aguarde o status **Succeeded** em **Installed Operators**.

> **Não use o Kueue embutido.** O estado `Managed` do Kueue no DataScienceCluster está depreciado e é incompatível com o Red Hat build of Kueue. Os dois juntos geram controladores em conflito. Com o OpenShift AI 3.5, use **`Unmanaged`** (Fase 7).

### 4.2 Criar o Kueue CR

Você tem duas opções:

- **Opção A (mais simples):** deixe o OpenShift AI criar. Com `kueue.managementState: Unmanaged` no DataScienceCluster, o operador do OpenShift AI cria um Kueue CR padrão se não existir nenhum.
- **Opção B (controle explícito):** crie você mesmo antes da Fase 7. O nome precisa ser `cluster`:

```yaml
apiVersion: kueue.openshift.io/v1
kind: Kueue
metadata:
  name: cluster
  namespace: openshift-kueue-operator
spec:
  managementState: Managed
  config:
    integrations:
      frameworks:
      - BatchJob
      - Deployment      # workloads de serving
      - Pod
      - LeaderWorkerSet # só se usar LWS
    preemption:
      preemptionPolicy: Classical
```

> **Validar:** quais `frameworks` o Kueue precisa para enxergar os pods do `LLMInferenceService` não está explícito na documentação do 3.5. Esse é o mesmo ponto em aberto da seção 5 da arquitetura. Se optar pela Opção A, confira depois com `oc get kueue cluster -n openshift-kueue-operator -o yaml` quais integrações vieram habilitadas.

Verificação:

```bash
oc get kueue -A
oc get pods -n openshift-kueue-operator
# kueue-controller-manager-*      1/1 Running
# openshift-kueue-operator-*      1/1 Running
```

> **Filas e namespaces:** ResourceFlavors, ClusterQueues, LocalQueues, WorkloadPriorityClasses e os labels `kueue.openshift.io/managed=true` nos namespaces ficam para depois, conforme a seção 5 da arquitetura. Lembre: no OpenShift AI 3.5, **shared cohorts não são suportados**.

## Fase 5: LeaderWorkerSet Operator (opcional)

Só é necessário quando um único servidor de modelo usa **mais de 8 aceleradores** (deploy multi-nó). Na arquitetura proposta, cada réplica usa 2 ou 4 GPUs dentro de um nó, então **pode pular**.

Se for instalar:

1. No web console, abra **Ecosystem → Software Catalog** (OpenShift 4.20+) ou **Operators → OperatorHub** (4.19), procure **Red Hat build of Leader Worker Set** e instale no namespace sugerido (`openshift-lws-operator`).
2. **Crie o `LeaderWorkerSetOperator` CR** com os valores padrão.
3. Verifique: em *Installed Operators*, projeto `openshift-lws-operator`, o operador deve mostrar `Condition: Available`.

## Fase 6: Red Hat Connectivity Link (Kuadrant + Authorino)

Necessário para a autenticação do llm-d e para o MaaS. O MaaS pede **Red Hat Connectivity Link 1.4.x no namespace `openshift-operators`** e **Kuadrant 1.4.2 ou superior**.

### 6.1 Instalar o operador

1. No web console, abra **Ecosystem → Software Catalog** (OpenShift 4.20+) ou **Operators → OperatorHub** (4.19).
2. Procure **Red Hat Connectivity Link** e clique em **Install**.
3. Em **Installation mode**, escolha **All namespaces on the cluster** (namespace `openshift-operators`).
4. Escolha um canal que entregue a versão **1.4.x**, mantenha a aprovação automática e clique em **Install**.
5. Aguarde o status **Succeeded**. O operador instala como dependências o Authorino, o Limitador e o DNS Operator.

### 6.2 Criar o Kuadrant

```bash
oc create namespace kuadrant-system

oc apply -f - <<EOF
apiVersion: kuadrant.io/v1beta1
kind: Kuadrant
metadata:
  name: kuadrant
  namespace: kuadrant-system
EOF

oc wait Kuadrant -n kuadrant-system kuadrant --for=condition=Ready --timeout=10m
```

### 6.3 Habilitar TLS no Authorino

```bash
# 1. Certificado emitido pela CA de serviço do OpenShift
oc annotate svc/authorino-authorino-authorization \
  service.beta.openshift.io/serving-cert-secret-name=authorino-server-cert \
  -n kuadrant-system --overwrite

# 2. Aguardar o secret
oc get secret authorino-server-cert -n kuadrant-system

# 3. Authorino com listener TLS
oc apply -f - <<EOF
apiVersion: operator.authorino.kuadrant.io/v1beta1
kind: Authorino
metadata:
  name: authorino
  namespace: kuadrant-system
spec:
  replicas: 1
  clusterWide: true
  listener:
    tls:
      enabled: true
      certSecretRef:
        name: authorino-server-cert
  oidcServer:
    tls:
      enabled: false
EOF

# 4. Confiar na CA do cluster (exigido pelo MaaS)
oc -n kuadrant-system set env deployment/authorino \
  SSL_CERT_FILE=/etc/ssl/certs/openshift-service-ca/service-ca-bundle.crt \
  REQUESTS_CA_BUNDLE=/etc/ssl/certs/openshift-service-ca/service-ca-bundle.crt

oc wait --for=condition=ready pod -l authorino-resource=authorino \
  -n kuadrant-system --timeout=150s
```

Verificação:

```bash
oc get kuadrant -n kuadrant-system
oc get authorino authorino -n kuadrant-system -o jsonpath='{.spec.listener.tls.enabled}{"\n"}'   # true
oc get svc authorino-authorino-authorization -n kuadrant-system -o yaml | grep serving-cert-secret-name
```

> **Se o OpenShift AI já estava instalado antes do Connectivity Link**, reinicie os controladores depois desta fase:
> ```bash
> oc delete pod -n redhat-ods-applications -l app=odh-model-controller
> oc delete pod -n redhat-ods-applications -l control-plane=kserve-controller-manager
> ```

## Fase 7: Operador do OpenShift AI e DataScienceCluster

### 7.1 Instalar o operador

1. No web console, abra **Ecosystem → Software Catalog** (OpenShift 4.20+) ou **Operators → OperatorHub** (4.19).
2. Procure **Red Hat OpenShift AI** e clique em **Install**.
3. Escolha o canal da versão 3.5 (por exemplo, `stable-3.5`) e mantenha o namespace `redhat-ods-operator`.
4. Clique em **Install** e aguarde o status **Succeeded**.
5. **Não crie o DataScienceCluster pelo formulário ainda.** Use o YAML do passo 7.2.

Verificação:

```bash
oc get dscinitialization        # default-dsci criado automaticamente
```

### 7.2 Criar o DataScienceCluster

Habilite só o necessário para esta arquitetura. **Ainda não habilite o MaaS** (isso é a Fase 10, depois do PostgreSQL e do gateway).

```yaml
apiVersion: datasciencecluster.opendatahub.io/v2
kind: DataScienceCluster
metadata:
  name: default-dsc
spec:
  components:
    dashboard:
      managementState: Managed
    kserve:
      managementState: Managed       # KServe + controlador do LLMInferenceService (llm-d)
    kueue:
      managementState: Unmanaged     # integra com o Red Hat build of Kueue
      # autoCreateQueues omitido (padrão false): filas gerenciadas por você
    aigateway:
      managementState: Removed       # vira Managed na Fase 10
      modelsAsAService:
        managementState: Removed
    ogx:
      managementState: Removed       # Managed na Fase 10 se quiser a UI de MaaS para usuários
    aipipelines:
      managementState: Removed
    feastoperator:
      managementState: Removed
    mlflowoperator:
      managementState: Removed
    modelregistry:
      managementState: Removed
    ray:
      managementState: Removed
    trainer:
      managementState: Removed
    trainingoperator:
      managementState: Removed
    trustyai:
      managementState: Removed
    workbenches:
      managementState: Removed       # Managed se for usar workbenches
```

```bash
oc apply -f default-dsc.yaml
oc get datasciencecluster default-dsc -w      # aguarde Phase: Ready
```

Notas:

- **`autoCreateQueues`** é `false` por padrão no 3.5. Mantenha assim: a arquitetura usa filas próprias (uma por ambiente e tipo de GPU).
- **Habilite outros componentes** (workbenches, pipelines etc.) só se for usá-los. Cada componente tem seus próprios pré-requisitos.

### 7.3 Ajuste pós-instalação das GPUs

```bash
oc delete configmap migration-gpu-status -n redhat-ods-applications --ignore-not-found
oc rollout restart deployment/rhods-dashboard -n redhat-ods-applications
```

### 7.4 Habilitar Kueue no dashboard

```bash
oc patch odhdashboardconfig odh-dashboard-config \
  -n redhat-ods-applications --type merge \
  -p '{"spec":{"dashboardConfig":{"disableKueue":false}}}'
```

> Com isso, todo projeto **novo criado pelo dashboard** recebe o label `kueue.openshift.io/managed=true` e uma LocalQueue padrão. Como a arquitetura usa LocalQueues próprias, prefira criar os namespaces via `oc`/GitOps com os labels e filas certos, ou ajuste a fila criada automaticamente.

Verificação da fase:

```bash

oc get pods -n redhat-ods-applications
oc get pods -n redhat-ods-applications | grep -E 'kserve-controller|llmisvc-controller|odh-model-controller'
oc get datasciencecluster default-dsc \
  -o jsonpath='{.status.conditions[?(@.type=="KueueReady")]}{"\n"}'        # reason Unmanaged
oc get deployments -n redhat-ods-applications | grep kueue                 # deve vir vazio
```

## Fase 8: gateway de inferência do llm-d

O llm-d precisa de um `GatewayClass` e de um `Gateway` chamado `openshift-ai-inference` em `openshift-ingress`. O Service Mesh 3 (que implementa o Gateway API no OpenShift) já vem instalado por padrão no OpenShift 4.20 ou superior. **O OpenShift Service Mesh v2 não pode estar instalado.**

```bash
oc get gatewayclass
oc get gateway -n openshift-ingress
```

Se o gateway não existir, crie-o restrito por label de namespace (nunca `from: All`):

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: openshift-ai-inference
  namespace: openshift-ingress
  labels:
    istio.io/rev: openshift-gateway
spec:
  gatewayClassName: openshift-ai-inference   # ou openshift-default, conforme o GatewayClass disponível
  listeners:
  - name: https
    port: 443
    protocol: HTTPS
    allowedRoutes:
      namespaces:
        from: Selector
        selector:
          matchLabels:
            inference-gateway-access: "true"
    tls:
      mode: Terminate
      certificateRefs:
      - name: openshift-ai-inference-tls
```

```bash
oc apply -f openshift-ai-inference.yaml
oc label ns openshift-ingress inference-gateway-access=true

# Namespaces de modelos (criados depois, conforme a arquitetura)
for ns in prod-flashnext prod-qwen35 hml-flashnext hml-qwen35; do
  oc label ns $ns inference-gateway-access=true --overwrite
done

oc get gateway openshift-ai-inference -n openshift-ingress -o wide   # PROGRAMMED=True
oc get pods -n openshift-ingress -l gateway.networking.k8s.io/gateway-name=openshift-ai-inference
```

> **Bare metal:** por padrão o gateway usa um Service `type: LoadBalancer`. Sem suporte a LoadBalancer no cluster, use MetalLB ou confirme que o controlador criou uma Route.

> **Não anexe outras HTTPRoutes a este gateway** (INFERENG-6962): elas fazem o EndpointPicker ser ignorado e desligam o roteamento inteligente e o flow control.

## Fase 9: preparação do MaaS (PostgreSQL, gateway e TLS)

### 9.1 PostgreSQL

O MaaS precisa de um **PostgreSQL 14 ou superior**, acessível pela rede do cluster, para armazenar API keys, subscriptions e uso. **O OpenShift AI não fornece esse banco**: provisione um (externo ou gerenciado) antes de seguir.

O secret é criado no namespace de infraestrutura do MaaS (padrão `redhat-ai-gateway-infra` no 3.5). Criar o secret **antes** de habilitar o MaaS evita ter de reiniciar o `maas-api` depois:

```bash
oc create namespace redhat-ai-gateway-infra --dry-run=client -o yaml | oc apply -f -

oc create secret generic maas-db-config \
  -n redhat-ai-gateway-infra \
  --from-literal=DB_CONNECTION_URL='postgresql://<usuario>:<senha>@<host>:5432/<banco>?sslmode=require'

oc get secret maas-db-config -n redhat-ai-gateway-infra
```

> Se o namespace de infraestrutura for diferente no seu ambiente, descubra depois de habilitar o MaaS com:
> `oc get maastenantconfig default-tenant -n models-as-a-service -o jsonpath='{.status.infraNamespace}'`

### 9.2 Gateway do MaaS

O MaaS exige um `Gateway` chamado **`maas-default-gateway`** em **`openshift-ingress`**, usando o GatewayClass `openshift-default` (controlador `openshift.io/gateway-controller/v1`), com duas anotações obrigatórias:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: openshift-default
spec:
  controllerName: openshift.io/gateway-controller/v1
---
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: maas-default-gateway
  namespace: openshift-ingress
  annotations:
    opendatahub.io/managed: "false"                        # impede o ODH de sobrescrever as políticas do MaaS
    security.opendatahub.io/authorino-tls-bootstrap: "true" # TLS entre gateway e Authorino
spec:
  gatewayClassName: openshift-default
  listeners:
  - name: https
    hostname: "maas.<dominio-apps-do-cluster>"
    port: 443
    protocol: HTTPS
    allowedRoutes:
      namespaces:
        from: Selector                 # nunca From: All (RHOAIENG-80360)
        selector:
          matchLabels:
            maas-gateway-access: "true"
    tls:
      mode: Terminate
      certificateRefs:
      - name: maas-default-gateway-tls
```

```bash
# Crie o GatewayClass só se ele ainda não existir
oc get gatewayclass openshift-default || oc apply -f gatewayclass-openshift-default.yaml

oc apply -f maas-default-gateway.yaml

# Namespaces que poderão anexar rotas ao gateway do MaaS
oc label ns redhat-ai-gateway-infra maas-gateway-access=true --overwrite
for ns in prod-flashnext prod-qwen35 hml-flashnext hml-qwen35; do
  oc label ns $ns maas-gateway-access=true --overwrite
done

oc get gateway maas-default-gateway -n openshift-ingress          # PROGRAMMED=True
oc get gateway maas-default-gateway -n openshift-ingress \
  -o jsonpath='{.metadata.annotations.security\.opendatahub\.io/authorino-tls-bootstrap}{"\n"}'   # true
```

> **Validar o seletor:** a documentação proíbe `from: All`, mas não fixa um label único para o gateway padrão do MaaS (no multi-tenant ela usa `maas.opendatahub.io/gateway-access-<tenant>=true`). O `maas-gateway-access=true` acima é um exemplo; garanta que **o namespace de infraestrutura do MaaS e os namespaces dos modelos** tenham o label escolhido. O *Models-as-a-Service companion guide* da Red Hat tem manifests de exemplo para esse passo.

> **Sem LoadBalancer:** verifique se o controlador criou uma Route; senão, crie uma manualmente apontando para o Service do gateway:
> `oc get route -n openshift-ingress -l gateway.networking.k8s.io/gateway-name=maas-default-gateway`

### 9.3 TLS entre gateway e Authorino

Já feito na Fase 6.3 (certificado, listener TLS e variáveis `SSL_CERT_FILE`/`REQUESTS_CA_BUNDLE`) e na anotação do gateway acima. Na Fase 10, o controlador do MaaS detecta a anotação e cria o `EnvoyFilter` que faz o Envoy falar TLS com o Authorino.

## Fase 10: habilitar o MaaS

### 10.1 DataScienceCluster

No OpenShift AI 3.5, o MaaS fica em **`spec.components.aigateway.modelsAsAService`** (o campo antigo `kserve.modelsAsService` está depreciado).

```bash
oc patch datasciencecluster default-dsc --type merge -p '{
  "spec": {"components": {
    "aigateway": {"managementState": "Managed",
                  "modelsAsAService": {"managementState": "Managed"}},
    "ogx": {"managementState": "Managed"}
  }}}'
```

- **`aigateway`**: liga o operador do AI Gateway.
- **`modelsAsAService`**: liga o controlador e os recursos do MaaS.
- **`ogx`**: necessário só para as telas de MaaS **para usuários** no dashboard (Gen AI Studio). Pode manter `Removed` se os usuários só usarem a API.

### 10.2 Dashboard

```bash
oc patch odhdashboardconfig odh-dashboard-config -n redhat-ods-applications --type merge -p '{
  "spec": {"dashboardConfig": {
    "modelAsService": true,
    "maasAuthPolicies": true,
    "genAiStudio": true
  }}}'
```

| Flag | Para quê |
|---|---|
| `modelAsService` | Recursos de MaaS no dashboard |
| `maasAuthPolicies` | Telas de administração (subscriptions, authorization policies) |
| `genAiStudio` | Telas de usuário (exige `ogx: Managed`) |
| `vLLMDeploymentOnMaaS` | **Não habilite**: runtime vLLM no MaaS é Technology Preview. A arquitetura usa llm-d |
| `observabilityDashboard` | Dashboard de uso (Technology Preview); exige Cluster Observability Operator |
| `externalModels` | Modelos externos (Technology Preview); não usado aqui |

## Erros comuns

| Sintoma | Causa provável | Correção |
|---|---|---|
| Autenticação do llm-d não funciona | Pré-requisitos instalados fora de ordem | Recriar Gateway, Kuadrant e Authorino na ordem documentada e reiniciar os controladores (Fase 6) |
| Modelos inacessíveis depois de instalar o Connectivity Link | OpenShift AI instalado antes do Kuadrant | Reiniciar `odh-model-controller` e `kserve-controller-manager` |
| Tenant do MaaS `Degraded` | UWM desligado, secret do banco ausente ou Kuadrant não pronto | Ver checklist 11.3 |
| HTTP 429 no MaaS sem consumo | `MaaSAuthPolicy` sem `MaaSSubscription` | Criar a subscription correspondente |
| HTTP 403 no MaaS | `MaaSSubscription` sem `MaaSAuthPolicy` | Criar a authorization policy |
| Gateway sem rotear para o modelo | Namespace sem o label exigido pelo `allowedRoutes` | Aplicar o label no namespace do modelo |
| Kueue em conflito | Kueue embutido (`Managed`) junto com o Red Hat build of Kueue | Usar `managementState: Unmanaged` |
| Operador abre "ClusterExtensions" no console | Catálogo OLMv1 (OCP 4.21+) | Desabilitar o catálogo OLMv1 antes de instalar |
