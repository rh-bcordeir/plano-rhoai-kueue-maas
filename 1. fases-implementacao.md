# Fases de implementação

Sequência para implementar a arquitetura descrita em `arquitetura-llm-ocp.md`. O passo a passo detalhado das Fases 0 e 1 está em `tutorial-pre-requisitos-rhoai.md`.

## Fase 0: pré-requisitos do cluster

- Instalar o NVIDIA GPU Operator e o NFD.
  - Confirmar os labels `nvidia.com/gpu.product` nos nós.
  - Rodar `nvidia-smi topo -m` nas RTX.
- Instalar o Red Hat build of Kueue e o cert-manager.
- Instalar o Red Hat Connectivity Link (Kuadrant 1.4.2 ou superior), exigido pelo MaaS.
- Habilitar o User Workload Monitoring.

## Fase 1: instalação do RHOAI 3.5

- Criar o `DataScienceCluster` com KServe/llm-d habilitados e o Kueue em `Unmanaged`.
- Criar os gateways do llm-d e do MaaS sem `allowedRoutes.namespaces.from: All`.

## Fase 2: Kueue (Opcional)

- Criar os namespaces com os labels.
- Criar os ResourceFlavors.
- Criar os 2 ClusterQueues, um por tipo de GPU (`cq-h200` e `cq-rtx`), sem cohort, com produção e homologação na mesma fila.
- Criar as LocalQueues e as WorkloadPriorityClasses.
- Criar os hardware profiles.

**Validação antes de seguir:** confirmar que o Kueue admite um `LLMInferenceService`. Se não admitir, aplicar o plano B (ResourceQuota, PriorityClass e taints).

## Fase 3: deploy em homologação e teste de carga

- Subir `hml-qwen35` e `hml-flashnext`.
- Validar memória, inicialização e a versão do vLLM.
- Comparar TP4 com TEP4 no Qwen3.5.
- Medir quantos tokens por minuto cada réplica entrega dentro do SLO.

## Fase 4: deploy em produção

- Subir `prod-qwen35` e `prod-flashnext` com o número fixo de réplicas definido pelo teste de carga.

## Fase 5: MaaS

- Publicar os modelos.
- Criar os grupos, as subscriptions, as authorization policies e as API keys.
- Definir os limites de token com base nos números medidos na Fase 3.
